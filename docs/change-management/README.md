# Change Management Process

This guide formalizes how we request, evaluate, approve, and track any change in the ecommerce platform. The process satisfies the Release Manager requirement for traceability, risk control, and auditable rollbacks.

## 1. RFC (Request for Change)

1. **Initiate** an RFC using the template in [`rfc-template.md`](rfc-template.md). One RFC per deployable change set.
2. **Store** the RFC in the `docs/change-management/rfcs` folder or in the team’s knowledge base (link in the template).
3. **Attach** impacted Jira tickets, design docs, test plans, and rollback references (see [`../operations/rollback-playbooks.md`](../operations/rollback-playbooks.md)).

## 2. Approval Workflow

| Step | Role | Responsibility | Tool |
|------|------|----------------|------|
| Draft | **Requester / Feature Owner** | Complete RFC template, propose deployment window, define validation tests. | RFC doc |
| Impact Review | **SRE** | Evaluate risks, confirm monitoring/rollback readiness, update RTO/RPO if needed. | RFC doc + rollback playbooks |
| Approval | **Release Manager** | Validate scope, confirm calendar availability, sign-off or request changes. | Change calendar |
| CAB (optional) | **Architecture/Stakeholders** | Required for critical/high-risk changes or production downtime. | Meeting notes attached to RFC |

A change is approved only after Release Manager signature plus any required CAB notes.

## 3. Change Calendar

All approved changes are tracked in [`change-calendar.md`](change-calendar.md). Each entry includes:

- Change ID (RFC short code).
- Planned date/time window.
- Owner and backup engineer.
- Status (Planned / In Progress / Complete / Rolled Back / Blocked).
- Link to Jenkins build or deployment record.

Update the calendar immediately after each change: include actual start/end times, whether rollback was exercised, and incident outcomes.

## 4. Rollback Procedures

Rollback actions are documented per service in [`../operations/rollback-playbooks.md`](../operations/rollback-playbooks.md). Every RFC must reference the appropriate section and state the expected RTO/RPO. The Jenkins pipelines now trigger automatic rollbacks on failure; for manual drills run `jenkins/scripts/rollback-services.sh` as documented.

## 5. Automation & Tooling

- **Release Notes Automation:** `jenkins/scripts/generate-release-notes.sh` produces categorized notes from conventional commits and publishes GitHub Releases. Jenkins notifies the `#releases` Slack channel automatically.
- **Conventional Commits Enforcement:** see [`../development/conventional-commits.md`](../development/conventional-commits.md) and the `hooks/commit-msg.sh` hook to keep commit history structured for automated notes.
- **Change Evidence:** Attach Jenkins build URLs, Sonar/Trivy reports, and rollback confirmations to the RFC before closing.

## 6. Change Lifecycle Checklist

1. Draft RFC.
2. Peer review & SRE impact assessment.
3. Schedule in calendar; obtain Release Manager approval.
4. Execute change following the pipeline and rollback playbooks.
5. Update calendar + RFC with results, metrics, and any follow-up actions.
6. Notify stakeholders via release automation.

Keep this document updated whenever tooling or roles change.
