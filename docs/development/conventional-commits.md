# Conventional Commits & Commit Hook

To enable automated release notes, we now enforce the [Conventional Commits](https://www.conventionalcommits.org/) specification.

## Format

```
<type>(<scope>)!: <short summary>

<body>
<footer>
```

- **type**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- **scope** (optional): component or service (`user-service`, `infra`, `jenkins`, etc.).
- Add `!` for breaking changes or include `BREAKING CHANGE:` in the footer.

### Examples
- `feat(api-gateway): add rate limiting headers`
- `fix(product-service): handle null discounts`
- `refactor(jenkins): extract rollback helper`
- `feat!: remove legacy auth endpoints`

## Commit Hook

The repo provides `hooks/commit-msg.sh` to validate messages locally.

```bash
ln -sf ../../hooks/commit-msg.sh .git/hooks/commit-msg
chmod +x hooks/commit-msg.sh
```

The hook blocks commits that do not match the regex:

```
^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([\w\-.]+\))?(!)?: .+
```

## Why it Matters

- The Jenkins release stage parses commit types to build categorized release notes (Features, Bug Fixes, Breaking Changes, etc.).
- Change Management uses the same metadata to populate the release calendar and CAB reviews.
- Consistent commit messages make it easier to identify risky changes and trigger automated rollbacks if needed.

## Exceptions

For merges generated by GitHub or emergency hotfixes you can bypass the hook by setting `SKIP_CONVENTIONAL_COMMITS=true` before the commit, but you must document the reason in the RFC.
